# Running the Mac side without a terminal

Today everything about the service on the Mac is a CLI command: `setup`, `install` and the `launchctl`
lines it prints, `doctor`, `deploy`, `rollback`. That is fine for someone who lives in a terminal and
hard for anyone else. This note adds three screens over one set of operations:

1. **This Mac**, a page in Settings on the web app and the iPhone app: what `doctor` checks, which build
   runs, the recent warnings and errors, and two buttons, Restart and Roll back.
2. **A setup wizard in the browser**, `workoffdesk setup --web`, for the first install: checks, account,
   address, service, then a QR code for the phone.
3. **A menu bar app** for the Mac: the service's state at a glance, its checks, start, stop, restart, the
   address as a QR code.

## One set of operations

Every screen reads and does the same things, each written once in the server package:

| What | Where |
| --- | --- |
| The checks | `doctor.ts` `runDoctor`, plus a `codex` check that never fails (Codex is optional) |
| Which build runs, the releases kept | `release.ts` `listReleases`, `build.ts` `readBuildStamp`, the `.activated` file |
| Warnings and errors | `ops/problems.ts`: the newest 50 lines of level warn or above in `logs/workoffdesk.log` (and `.1`) |
| Start, stop, restart | `ops/service.ts`: `launchctl bootstrap`, `bootout`, and the SIGTERM-then-kickstart restart that `release.ts` already does |
| The last restart or rollback and how it ended | `ops/lastOp.ts`: `ops.json` in the service's home |

The checks' words come from `messages.ts`, picked by the request's `Accept-Language` for the phone
(`messagesFor`), by the Mac's language for the CLI, as now.

## This Mac

`GET /api/mac` (signed in, like every route) answers the report:

```ts
type MacReport = {
  checks: Check[];                 // runDoctor, in the reader's language
  version: string;                 // this server's
  build: BuildStamp | null;        // dist/build.json
  release: string | null;          // the release `app` points at
  releases: { name: string; version: string; activatedAt: string | null }[]; // newest first
  rollbackTo: string | null;       // the release rollback would go to now
  managed: boolean;                // launchd runs this process as config.serviceLabel
  startedAt: number;               // when this process started, so a client sees a restart
  lastOp: LastOp | null;
};
type LastOp = { op: 'restart' | 'rollback'; startedAt: number; finishedAt?: number; ok?: boolean; message?: string };
```

`GET /api/mac/problems` answers `{ at: string; level: 'warn' | 'error' | 'fatal'; msg: string; detail: string }[]`,
newest first. The log is pino's, so the paths in `REDACT` are already censored; `detail` is the rest of the
line as JSON, cut at 4 KB.

`POST /api/mac/restart` and `POST /api/mac/rollback {to}` answer 202 and hand the work to a helper process:
a server cannot restart itself, since the moment it exits nothing is left to finish. The helper is the same
CLI the service runs (`process.argv[1]`), `restart --record` or `rollback --record`, spawned detached in its
own process group. launchd kills a job's process group when it stops the job, not other groups: checked on
macOS 26 with a throwaway agent whose detached child outlived `kill`, `kickstart -k` and `bootout`. The
helper writes `ops.json` when it starts and again with the outcome. The routes refuse with 409:

- `not-managed`: this server was started by hand (`workoffdesk serve`), not by launchd, so there is no
  service to restart. launchd sets `XPC_SERVICE_NAME` to the job's label; the server compares it with
  `config.serviceLabel` (checked with the same agent).
- `op-busy`: `ops.json` names an operation that has not finished and whose helper is still alive.
- `rollback-moved`: `to` is not the release `rollback` would go to now (another deploy came in between).
  The page names the release it goes back to, so a confirmation must still be true when it arrives.

Restarting does not end sessions: they are tmux sessions on the service's own socket (facts.md, Sessions).

The page, `/mac` on the web and `mac` in the app, is opened from a "This Mac" row in Settings:

- A summary line: "Everything works" or "N problems", then the failed checks first, each with its fix, which
  copies on a tap.
- The build: version, commit, when it began serving; the releases kept below it.
- Restart (one confirmation) and Roll back to the release before (two taps, naming the version). While one
  runs, the page polls `GET /api/mac` each second and ignores the failures of a server that is down, until
  `startedAt` moves and `lastOp` has finished, then shows how it ended; after 60 seconds it says the Mac did
  not come back. Both are disabled with the reason when `managed` is false.
- The recent warnings and errors, each opening to its detail.

The state lives in `libs/client/src/macPage.ts` (`createMacPage(api)`, a store like `projectSearch.ts`), so
the web and the app only draw it.

## The setup wizard

`workoffdesk setup --web` starts a second, short-lived server on `127.0.0.1` at a free port, opens
`http://127.0.0.1:<port>/setup#<token>` in the Mac's browser, and prints that address. It serves the web
app's build and `/api/setup/*`, and nothing else. There is no user yet, so no login can guard it; instead:

- The token is 24 random bytes, in the fragment (never sent in a request line, never logged). The page moves
  it to `sessionStorage` and sends it as `x-setup-token`; a request without it is 403 (constant-time compare).
- The `Host` header must be `127.0.0.1:<port>`, which a page on another site reaching it through DNS
  rebinding cannot send; a write's `Origin` must be `http://127.0.0.1:<port>`.
- It listens on loopback only and exits when the wizard is done, on Ctrl-C, or after 30 minutes untouched.

Steps, each a call:

1. **Checks** (`GET /api/setup/state`): macOS, Node, tmux, Claude Code, each with its fix and Check again.
2. **Account** (`POST /api/setup/account {username, password}`): the rules `setup` has (a password of at
   least 12 characters); replacing a user signs every device out, as `setup` does.
3. **Address** (`POST /api/setup/address`): one of
   - Tailscale, when `tailscale` is installed and up: the Mac's `https://<name>.ts.net` from
     `tailscale status --json`, and `tailscale serve --bg <port>` run on the person's tap;
   - a Cloudflare tunnel they have (`cloudflared tunnel list`) and a hostname: `install --tunnel` writes its
     agent, and `cloudflared tunnel route dns` runs on their tap;
   - any other address, typed.
4. **Service** (`POST /api/setup/service`): what `install` writes, then `launchctl bootstrap` (or kickstart
   when already loaded), then waits for `/healthz` up to 30 seconds.
5. **Done**: the full `doctor`, and the address as a QR code for the phone's camera (`qrcode-generator`,
   drawn as SVG). Finish ends the wizard's server.

`install.sh` ends by running `workoffdesk setup --web` when it runs in a terminal and nothing is set up yet,
and prints the commands otherwise.

`install` keeps printing commands and starting nothing; the work it does moves into `installService()` in
`install.ts`, which both it and the wizard call.

## CLI additions

- `workoffdesk start`, `stop`, `restart`: the service through launchd (bootstrap or kickstart; bootout; the
  graceful restart). `restart` and `rollback` take `--record` (the helper's flag).
- `workoffdesk status --json`: `{ checks, version, build, release, releases, rollbackTo, lastOp, problems, origin, port,
  running, home }`,
  what the menu bar app shows. `doctor` stays as it is.
- `workoffdesk setup --web`.

## The menu bar app

`apps/mac`, a Swift package (`swift build`), SwiftUI `MenuBarExtra`, macOS 13 or later. It runs the CLI,
never its own copy of the logic: `workoffdesk status --json` when the menu opens and every 60 seconds, and
`start`, `stop`, `restart` on a tap. It finds the CLI at `~/.local/bin/workoffdesk` (what `install`
writes), then on `PATH`'s usual places. The icon shows running, a problem, or stopped. The menu shows the
version, the failed checks with their fixes (copied on a click), the recent errors, Open in browser, the
QR code (Core Image), Open logs folder, Open at login (`SMAppService`), Quit. Words in English and Chinese,
following the Mac.

`apps/mac/scripts/build-app.sh` makes `WorkOffDesk.app` (a `LSUIElement` agent, ad-hoc signed) in
`apps/mac/build/`. Signing with a Developer ID and notarizing, for handing the app to others, needs an
Apple Developer account and is left to whoever releases it.

## Not in this round

Changing settings other than the address (port, sleep, Claude's arguments), a live log, uninstalling from a
screen, an Intel-and-Apple universal build of the menu bar app.

## Testing

Server: unit tests for the problems reader (levels, rotation into `.1`, a cut-off last line, the 50 cap), the
op record (busy while the helper lives, free when it died), the routes (signed out 401, `not-managed`,
`op-busy`, `rollback-moved`, the helper spawned with the right arguments), the wizard's guard (no token,
wrong token, wrong Host, wrong Origin, token in the fragment only), and the CLI's `status --json` shape.
Client: `createMacPage` (the poll through a server that is down, the 60-second limit, an answer after the
page is let go). The screens are checked by looking at them: the web page headless, the app in the
simulator, the menu bar app on the Mac.
