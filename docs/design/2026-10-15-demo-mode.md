# A demo to try the app without a Mac

The iPhone app is useful only once it is signed in to workoffdesk on a Mac. Someone without one at hand (a person
deciding whether to set it up, or someone reviewing the app for a store) sees a sign-in form and nothing past it.

## What holds

Without a Mac, the app can be tried as it is used: a list of sessions, a Claude session's chat with its tool calls,
a sub-agent's conversation, a message sent and answered, a reply stopped, a session started and ended. All of it is
the app's own screens and client, fed by a Mac simulated on the phone, and the app says throughout that it is a demo.

## Who already knows

- The client reaches the Mac through two seams only: `api` (requests, `libs/client/src/base/api.ts`, which calls
  `fetch`) and `open` (sockets, `OpenSocket` in `libs/client/src/base/platform.ts`). Everything above them (the
  journal copy, the session list, the session line, the chat feed) is shared by the app and the web and stays as it
  is.
- What a session's page shows comes only from its journal copy, changed only by the Mac's rows
  (`docs/design/2026-10-06-session-journal-design.md`). A simulated Mac that writes rows the way the Mac does is
  drawn the way a real one is, and the protocol's types (`JournalRow`, `JournalSync`, `Push`, `TermSession`,
  `ChatItem`) say what it must write.
- An account is a server and a token (`Login`, `apps/mobile/src/client.ts`). The demo is one more account, on the
  address `demo:`, which no real server has.

## Design

- `libs/client/src/demo/` holds the simulated Mac: `createDemoMac({ lang })` gives `fetch` and `open` with the
  shapes of the real ones. It keeps sessions and a journal per session in memory, with a new epoch each time it is
  made, so a copy kept on the phone from an earlier demo starts over.
  - `/api/events` (socket) and `/api/events/now`: the session list, sent again on each change, with journal heads.
  - A session's socket: catch-up from the version the phone says it has, then each row as it is written. Esc or
    ^C sent on it stops a reply under way, as Claude Code does, with an "interrupted" note.
  - `…/journal`, `…/journal/items`, `…/messages`: the journal sync, older items (none) and a message sent. A
    message is answered by a short scripted turn: the message lands as a turn, Claude works (a status, a tool call
    and its result, a live line), then replies saying this is a demo and what a real Mac would do, and goes idle.
  - Sessions: list, start (Claude or Codex in one of the demo's folders), end, rename, pin.
  - A sub-agent's description and conversation, and a conversation's chat, for the sub-agent page.
  - Requests the app makes on its own (push registration, slow reports, the chat's numbers, logins) are taken
    and do nothing.
  - Anything else answers 409 with the code `demo`, which the app says as "Not in the demo: connect your Mac to do
    this."
- What the demo shows: three sessions in two made-up projects.
  - A Claude session that changed a login button: reads, an edit with its diff, a test run, a sub-agent with its
    own conversation, the changed-files card and the reply.
  - A Claude session that works while it is looked at: a task list ticking over, a command running, then a reply.
    It starts over each time the demo starts.
  - A Codex session, idle, with one exchange.
  The content is in the app's language, English or Chinese, read when the demo starts.
- `api` takes an optional `fetch`; the app's `api` and `open` go to the simulated Mac while the account in use is
  the demo, and to the network otherwise. The demo is the login in use, kept so the app opens in it again, but it
  is not one of the accounts kept, nor the address the sign-in form offers next time. Leaving it (sign out)
  returns to the sign-in form. Nothing of it goes over the network.
- The sign-in form offers "Try the demo" under its button, and so does the form that adds an account, so someone
  signed in can try it and sign out of it back to their account. While the demo is in use the session list says so above
  the sessions: "Demo: made-up sessions, no Mac connected", with "Connect my Mac", which leaves the demo for the
  sign-in form.

## Not in this

- The web app: it is served by the Mac it talks to, so it is never without one.
- Pictures, files, voice, the Mac's page, conversations on the Mac, account moves and the terminal's screen: they
  answer as not in the demo.

## Tests

- Client, `libs/client/tests/demo/demoMac.test.ts`, the real client (journals, session list, session line) on the
  simulated Mac, on fake timers:
  - the list has the three sessions, and a started session joins it and an ended one leaves it;
  - a session's copy syncs to its items, and a copy from an earlier demo (another epoch) starts over;
  - a message sent lands as a turn and is answered, the status going working then idle, with the rows pushed on
    the session's line as they are written;
  - Esc while answering stops the reply with an interrupted note, and the session is idle;
  - a sub-agent's description and conversation are answered;
  - an unknown request is refused with the code `demo`, which the app's error text says in words.
- Accounts, `libs/client/tests/demo/account.test.ts`: the demo is told apart, and the app opens in it again without
  keeping it as an account.
